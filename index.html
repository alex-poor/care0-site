The headline bet · #1

The patient owns the record.
The practice is a consented reader.

Access is decided by who holds a key — and by nothing else. Not a server, not an ACL row, not row-level security. You can't leak what you can't decrypt.

→A granted reader fetches a sealed segment over the wire (peer-to-peer, iroh QUIC) and opens only the segments it holds a key-wrap for.
→Revocation is simply not wrapping the next key. It's real, not a policy promise — and every access is logged to the patient.
→A reviewed crypto substrate — X25519 + HKDF, ChaCha20-Poly1305 per segment — under a signed, hash-chained consent ledger as the tamper-evident authorization record.
→Third-party apps, a specialist, or a family member become consented readers the moment the patient wraps a key — revocable, audited, no central integration project.

This is the opposite of “harden the central DB”.

The Encounter spine · #5

One object replaces four

An appointment is a planned Encounter. The queue is just the arrived ones. The note, conditions, orders, prescriptions and the invoice all hang off the one object as it moves through its lifecycle.

Legacy needed a booking row + a note + a queue row + a visit header kept in sync. This is one lifecycle.
Auto-invoice on finish
The GP never “does billing”. Finishing the Encounter raises the invoice; subsidy is derived from the patient's funding.

Safety by construction · #6

Illegal states don't compile

Drug-interaction alerting is table-stakes. The differentiator is where the guarantee lives — in the type system, not in a runtime check someone can forget to call.

identifiers/src/nhi.rs
// An invalid NHI cannot be constructed — not even by
// deserializing bad JSON. The check digit is enforced
// at the type boundary.
pub struct Nhi(String);

impl Nhi {
    pub fn parse(s: &str) -> Result<Nhi, NhiError> {
        if !mod23_valid(s) {
            return Err(NhiError::CheckDigit);
        }
        Ok(Nhi(s.to_uppercase()))
    }
}
// A prescription can't be issued without a prescriber,
// an unsigned note can't be sent — enforced by typestates.
// #![forbid(unsafe_code)] · no unwrap/panic · SQL checked
// at build time · property-tested validators.

Architecture at a glance

A Rust modular monolith, built plugin-shaped

A thin kernel — config, Postgres pool, a typed domain-event bus, a capability registry, auth — is the only thing every module depends on. First-party modules are built against the same contracts third-party and AI plugins will use.

White-label & theming · #13

A design-token system, not a reskin

Every colour is a semantic role token in three segregated families — chrome, status, accent — so a theme is pure data. Pick a skin and watch this whole page re-colour. These starter skins are ported from AndroidAPS.

Status colours stay semantic even when the brand changes, so safety signals never get reskinned away. Each skin is WCAG-contrast-validated — an illegible palette is refused. White-label branding is resolved per tenant and injected server-side, so the first paint is already theirs.

See it in 2 minutes

Run it, seed it, drive a clinic day

  1. Boot it. Just Postgres is needed — migrations apply at startup, then open localhost:8080.
  2. Seed demo data — ~7 realistic patients, each with a finished consult (note + auto-invoice), coded conditions, observations, a prescription and a lab order.
  3. Search a name in the omnibox — Ngata, Patel, Williams — and open the longitudinal record.
  4. Start a visit → Diagnose and type diab / asthma — the SNOMED typeahead in action.
  5. Finish the encounter and check the balance — it auto-billed with the funding-derived subsidy.
  6. Ask a question — diabetics, care gaps, who owes money, dashboard, today's board, banking.
